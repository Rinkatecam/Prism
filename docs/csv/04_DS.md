## DS-100 — Three-thread collector pipeline (`collector_v2/`)

**Implements**: FS-001, FS-008, FS-122.

**Structure**:
```
  Supervisor (1 daemon)         Workers (15 daemons)            Aggregator (1 daemon)
  ┌────────────────────┐  Q1   ┌─────────────────────────┐  Q2  ┌───────────────────────┐
  │ tick every 5 s     │──────▶│ pull WorkItem           │─────▶│ pull Result           │
  │ select due checks  │       │ open WSMan session      │      │ persist to DB         │
  │ produce WorkItem   │       │ run PS via pypsrp       │      │ update state caches   │
  │ enqueue            │       │ enforce per-check       │      │ compute status        │
  │                    │       │   deadline              │      │ emit events / alerts  │
  └────────────────────┘       │ produce Result          │      │ record pulse          │
                               └─────────────────────────┘      └───────────────────────┘
```

Plus the **Periodics** thread (`collector_v2/periodics.py`) running fleet-wide jobs (TLS, drift, retention, health checks, failed-login collection, scheduled reports, auto-restart scanner, reboot janitor, LDAP probe).

**Why this design**:
- **Backpressure** — bounded `work_queue` means a stuck WinRM call cannot exhaust memory; supervisor pushes next-due-at 30 s into the future on queue-full.
- **Per-server failure isolation** — one bad target only burns one worker for at most its deadline (METRICS 30 s, LOGS 60 s, UPDATES 120 s, HARDWARE 60 s).
- **Single aggregator** = no concurrent writes to `metrics` etc. The aggregator is the sole writer of module-level dicts (`_previous_status`, `_baseline_dev_history`, `_recent_events`) so those need no locks.
- **5-second supervisor tick** balances responsiveness with overhead.
- **Hash-shard offsets** on first scheduling — spreads the "logs every 5 min" cadence across the fleet so all 30 servers don't fire LOGS on the same tick.
- **Bulletproof outer try/except** on every thread loop — the threads must never die. If they do, the watchdog (DS-150) records it.

**Reference**: `appendix_A_collector_inventory.md`.

## DS-101 — Per-server scheduling state (`ServerHealth`)

**Implements**: FS-001, FS-122.

**Structure**: `collector_v2/types.py:ServerHealth` is a dataclass per server holding:
- `name`
- `checks: dict[CheckType, CheckState]` — one entry per check type
- `accelerated_until: float`, `accelerated_reason: str`

Each `CheckState` carries: `next_due_at`, `last_ok_at`, `consecutive_failures`, `pending` flag.

**Why this design**:
- Replaces v1's monolithic `cycle_modulo` gating — each check type advances independently.
- **Exponential backoff** on consecutive failures (`types.backoff_delay_s(failures, base_s=60, cap_s=3600)`) — a chronically unreachable server isn't polled every 60 s, freeing worker capacity for healthy servers.
- **Acceleration** — `accelerate_server(name, duration_s, reason)` sets `accelerated_until`; while accelerated, all due checks fire on the next tick. Capped at `_ACCELERATE_MAX_DURATION_S = 1200 s` to prevent perpetual acceleration.

## DS-102 — Shared state module (`collector_v2/state.py`)

**Implements**: FS-001, FS-008, FS-121.

**Globals owned**:
- `server_health: dict[str, ServerHealth]` — supervisor is the writer, aggregator updates via `mark_check_completed`, API readers via `_server_health_lock`.
- `latest_by_server: dict[str, dict]` — dashboard's hot cache; aggregator writes, `_state_lock` for readers.
- `_pulse_buffer: deque (maxlen=1000)` — ECG widget feed; aggregator appends, `_pulse_lock` for snapshot reads.
- Heartbeats: `last_supervisor_tick`, `last_aggregator_tick`, `last_worker_activity_at` — per-thread, field-level updates (atomic in CPython).

**Why a separate module**: prevents circular imports (`supervisor` imports `state`, aggregator imports `state`, but neither imports the other). State is the dependency-graph sink.

## DS-103 — PowerShell sandbox (`ps_sandbox.py`)

**Implements**: FS-053.

**Structure**:
- `DEFAULT_ALLOWED_CMDLETS: frozenset[str]` (~92 cmdlets, lowercased).
- `HARD_DENY: tuple[regex]` — patterns rejected unconditionally regardless of allowlist.
- `validate_script(script, allowed_cmdlets=None, enabled=True) -> (ok, reason)`.

**Validation flow**:
1. If `enabled=False`, return `(True, "")`.
2. Match HARD_DENY patterns; reject on first match.
3. Tokenise; extract `Verb-Noun` identifiers; reject any not in allowlist.
4. Pass.

**Known limitations** (documented in module docstring):
- String concatenation (`&('I'+'nvoke-Expression')`).
- Char-code reconstruction (`[char]105+[char]101+[char]120` = `iex`).
- Backtick escapes (`In\`voke-Expression`).
- Allowlisted aliases (`gc`, `cat`, `Get-Content`) allow arbitrary file read.

**Mitigation** for structured fields (service name, process name, port): the `_run_ps_builder` path (DS-104) bypasses sandbox text-time inspection entirely by binding values as typed parameters.

## DS-104 — Parameter binding for workflow blocks

**Implements**: FS-054.

**Structure**: `workflow_engine.py:_run_ps_builder(wsman, builder)`. The `builder` closure receives the `PowerShell` object and calls `ps.add_script(literal_text).add_parameter(name, value)`. The user-supplied `value` is sent as a typed `[string]` argument and is never concatenated into the script body.

**Why this design**: closes the RCE vector that string-concatenation-based PS construction would expose, even if the sandbox is later compromised. Pinned by `test_workflow_param_binding.py`.

## DS-105 — Variable substitution (`{{step.X.output}}`)

**Implements**: FS-055.

**Structure**: `workflow_engine.py:_substitute_variables(text, executed, workflow)` + `_substitute_config_variables(config, executed, workflow)`. Substitution happens just-in-time at `_execute_graph` time, AFTER the prior step has run.

**Critical design decision**: `_substitute_config_variables` **excludes the `script` field** from substitution. Substituting variables into PS scripts would bypass the sandbox's text-time inspection (the sandbox sees the template, not the resolved text). This exclusion is pinned in `test_workflow_variables.py::test_substitute_config_skips_script_key`.

**Macros supported**: `{{step.<id>.output}}`, `{{step.<id>.success}}`, `{{step.<id>.error}}`, `{{workflow.name}}`, `{{workflow.id}}`. Unknown step/field references render as visible markers (`"unknown step 99"`) rather than silently empty — so operators see typos.

## DS-106 — Workflow execution graph

**Implements**: FS-050, FS-051, FS-057.

**Structure**:
- Canvas serialisation: Drawflow JSON (in `workflows.canvas_json`).
- Parsed in `workflow_engine.py:parse_canvas(canvas_json)` → `{nodes, start_nodes}`.
- Executed in `_execute_graph(...)`:
  - BFS through nodes from each `start_node`.
  - Per node, look up `BLOCK_EXECUTORS[node_type]` and invoke with `(config, server_map, db, settings)`.
  - Honours `node.data.disabled` (skip entirely) and `node.data._disabled_conns` (skip those connection IDs).
  - Output of each node captured into `executed: dict[node_id, (success, output)]`.

**Why BFS**: simple, deterministic execution order; AND/OR gates have explicit handling (require all/any predecessors complete).

## DS-107 — Install state lifecycle

**Implements**: FS-030, FS-033, FS-034, FS-037, FS-038.

**Structure**: `routes/api/_shared.py:_update_install_state: dict[server_name, dict]` persisted to `data/install_state.json`.

**State machine**:
```
None ─install kickoff─▶ installing ─progress─▶ restart_required ─restart fires─▶ rebooting
                                                  │
                                                  └─pending_reboot=False detected─▶ (popped)
rebooting ─first successful metric─▶ stabilising ─60 s window elapsed + next metric─▶ (popped)
rebooting ─20 min no metric (janitor)─▶ (popped, dashboard shows offline)
stabilising ─20 min no metric (janitor)─▶ (popped)
```

**Owners**:
- `installing`, `restart_required`, `completed`, `failed`: written by `_set_install_state` from `/update-status` and the install kickoff.
- `rebooting`: written by `_set_rebooting_state` after `/api/servers/<n>/power restart` and after auto-restart.
- `stabilising`: written by `aggregator._handle_post_reboot` on the first successful metric.
- All states auto-cleared by `aggregator._handle_updates_result` on `pending_reboot=False` (for `restart_required` / `completed` / `failed`) — added during this audit, see FS-037.
- Stuck `rebooting` / `stabilising` cleaned by `periodics._reboot_state_janitor` after 20 min — extended during this audit, see FS-038.

**Persistence**: every mutation writes `data/install_state.json` atomically (`tempfile.NamedTemporaryFile` + `os.replace`).

## DS-108 — Authentication architecture

**Implements**: FS-070, FS-071, FS-072, FS-073, FS-074, FS-115.

**Providers**:
- **LDAP/AD** via `ldap3` library; bind credentials encrypted in `config.json`.
- **Backup-admin** local account; password werkzeug-hashed in `config.json`.

**Session model**: Flask signed session cookie; `session['username']`, `session['login_time']`, `session['remember_me']`. Idle timeout 8 h default / 30 d remember-me / 15 min hard floor for backup-admin.

**Lockout**: `auth_failures` table; `auth.py` checks `db.count_recent_failures(username, window_minutes=30)` ≥ 10 → disable for 15 min.

**Forced termination**: `revoked_sessions` table keyed by `(username, login_time)`; checked on every request in `before_request`.

**Startup safety**: `assert_ldap_startup_safe` raises `SystemExit` if LDAP enabled but unreachable.

## DS-109 — RBAC architecture

**Implements**: FS-075, FS-076, FS-077.

**Levels**: `view` ⊂ `control` ⊂ `admin`.

**Storage**: `user_server_acl(username, server_name, permission)`. `server_name='*'` is a fleet-wide wildcard.

**Modes**:
- **Permissive** — when the ACL table is empty, all authenticated users are effectively admin. This is the legacy/initial mode. Tier-0 servers always require an explicit `admin` row even in permissive mode.
- **Enforced** — once any row exists, missing ACL = 403.

**Tier-0 dual-control**: each destructive endpoint calls `_require_server_permission(server, action)`. For tier-0 servers + destructive actions, the function additionally checks for a single-use approval token in `pending_approvals` (created by a second admin via `POST /api/approvals` and approved via `POST /api/approvals/<id>/decide`).

**Global destructive approval**: a `server_name='*'` approval is required for `/api/data/delete` and `/api/data/factory-reset`.

## DS-110 — Audit log architecture

**Implements**: FS-078, FS-079, FS-080, FS-081, FS-082.

**Storage**: `audit_log` table (schema in `appendix_D_db_schema.md`).

**Hash chain**:
```
prev_hash       = (previous row's row_hash) or '0' on the first row
row_hash        = SHA-256(prev_hash || timestamp || username || action ||
                          category || details || source_ip || session_id ||
                          request_id)
```

`Database.verify_audit_chain(limit=None)` walks the chain row-by-row, recomputing each hash and comparing to the stored `row_hash`. Detects deletion (gap in `id` sequence), tampering (recomputed hash mismatch), and out-of-order insertion.

**Append-only enforcement**:
```sql
CREATE TRIGGER audit_log_no_update BEFORE UPDATE ON audit_log
  BEGIN SELECT RAISE(ABORT, 'audit_log is append-only — UPDATE not allowed'); END;

CREATE TRIGGER audit_log_no_delete BEFORE DELETE ON audit_log
  BEGIN SELECT RAISE(ABORT, 'audit_log is append-only — DELETE not allowed'); END;
```

The triggers stop both intentional and accidental mutations from within the application. Out-of-process tampering (`sqlite3` CLI used directly against the file) is detected by the hash chain on next `verify_audit_chain()` call.

**JSONL mirror**: each successful `log_audit` insert also appends a JSON line to `data/audit_mirror.jsonl`. The mirror is append-only at the OS level (no truncation API used) and provides out-of-band evidence if `prism.db` is tampered with at the file system level.

**Forensic context** (auto-filled by `log_audit`):
- `source_ip` — `request.remote_addr` if in request, else `''`.
- `session_id` — SHA-256(`username + login_time`) for stable join key without exposing credentials.
- `request_id` — per-request UUID set by `app.py:_assign_request_id` in `before_request`.

## DS-111 — Anomaly detection cache architecture

**Implements**: FS-011, FS-012.

**Structure**: `analytics.py:_BASELINE_CACHE: dict[(server, segment), (ts, metrics)]`; `_BASELINE_CACHE_LOCK: threading.Lock`.

**Policy**:
- TTL: 5 min (`BASELINE_CACHE_TTL_S = 300.0`).
- Cap: 10 000 entries (`BASELINE_CACHE_MAX_ENTRIES`).
- On `recalculate_baselines` endpoint hit: `clear_baseline_cache()` is called so the next anomaly check uses fresh stats.

**Telemetry**: `_cache_hits`, `_cache_misses`, `_cache_evictions` counters; `get_baseline_cache_stats()` exposes them.

**Why caching**: the underlying `_compute_metric_stats(history)` walks ~168 h of metrics rows per server per anomaly check — expensive enough that the dashboard would lag without the cache.

## DS-112 — Maintenance window evaluation

**Implements**: FS-004.

**Structure**: `maintenance.py` is a stateless module. `_get_active_maintenance_window(server_name, settings)` evaluates:
1. Server in `window.servers`?
2. Today's weekday (0=Mon..6=Sun) in `window.days`?
3. Current HH:MM in `[start_time, end_time]`? (Wrap-over-midnight supported: `22:00 → 06:00`.)

All three must hold.

**Timezone**: `zoneinfo.ZoneInfo(settings['timezone'])`. If the timezone is invalid, the function returns `None` (no window active) rather than falling back to naive datetime (which would fire windows at the wrong wallclock time).

## DS-113 — Self-watchdog

**Implements**: FS-120.

**Structure**: `app.py:_watchdog_loop` daemon thread:
```python
while True:
    for name, thread in monitored_threads.items():
        if not thread.is_alive():
            db.log_audit(username='system',
                         action='watchdog_thread_died',
                         category='lifecycle',
                         details=f'thread={name}')
            _watchdog_state[name] = 'died'
    time.sleep(30)
```

Monitored threads:
- `restart-scheduler`
- `workflow-scheduler`
- `collector-v2-supervisor`
- `collector-v2-aggregator`
- (Workers and periodics are pool-managed; their stats counters are surfaced through `/api/system/health`.)

**Note**: this is best-effort observability. It does NOT auto-restart a dead thread — the operator is alerted via the audit log + health endpoint.

## DS-114 — Configuration loading

**Implements**: FS-123.

**Structure**: `config_manager.ConfigManager(config_path)`:
- `get_servers()` — reads `config.json`, decrypts passwords via `crypto_utils.decrypt_password`, returns list of `ServerConfig` dataclasses.
- `get_settings()` — same file (or `data/settings.toml` if used), with mtime-based cache (5 s TTL).
- `reload_config()` — force re-read.

Passwords are NOT cached — decrypted on every `get_servers()` call. This means a key rotation via `tools/rekey.py` takes effect on next cache invalidation (≤ 5 s).

**Encryption**: `crypto_utils.encrypt_password / decrypt_password` use a Fernet key stored at `data/.key` (or `PRISM_PASSWORD_KEY` env var override). Rotation: `tools/rekey.py` writes new key + re-encrypts all stored passwords + rewrites `config.json`.

## DS-115 — Workflow scheduler

**Implements**: FS-051, FS-052.

**Structure**: `workflow_engine.py:workflow_scheduler_loop(get_settings, db, get_servers)`:
- Tick every 30 s (`SCHEDULER_INTERVAL`).
- For each enabled workflow:
  - **Manual** → never fires automatically.
  - **Schedule** → `_should_trigger_scheduled` checks 2-min window vs configured time + day. Marker file in `data/` gates double-fire across the supervisor's tick boundary.
  - **Event** → `_evaluate_event_trigger` evaluates the configured condition against live metric cache (no fresh WinRM call — uses `state.latest_by_server`); compares to `_event_trigger_state[workflow_id].last_value`; fires only on `False → True` edge. 5 × `poll_seconds` debounce between fires.
- Successful fire calls `execute_workflow(db, workflow_id, ...)` which spawns a daemon thread.

**Why daemon-per-execution**: an execution can take many seconds (WinRM call latency); blocking the scheduler loop would starve other triggers.

## DS-116 — Frontend architecture

**Implements**: FS-007, FS-050, FS-056, FS-057, FS-058, FS-059, FS-101, FS-102.

**Approach**: server-rendered Jinja2 templates + HTMX for partial updates + vanilla JS for canvas-heavy pages (workflows.html, topology view) + Chart.js for charts.

**No bundler**: all JS is shipped as standalone files under `static/js/`; third-party libs (HTMX, Chart.js, Tailwind, Lucide, Drawflow) are loaded via CDN.

**Localisation**: `inject_locale` context processor exposes the translation dict `t` and the CSP nonce; templates use `{{ t.dashboard }}` etc. JS receives translations through a `PULSE_I18N` global populated by an inline `<script nonce>` block.

**CSP & nonces**: every inline `<script>` carries `nonce="{{ csp_nonce }}"`. `static/js/*.js` files are loaded without nonces (the CSP `script-src` allows `self` for them).

**Reduced motion**: `@media (prefers-reduced-motion: reduce)` block in `static/css/app.css` hides the pulse canvas; `static/js/pulse-monitor.js` respects the same query.

## DS-117 — PowerShell payload registry

**Implements**: FS-001, FS-015.

**Structure**: `collector_v2/scripts.py` contains five const strings — `PS_COLLECT_SCRIPT`, `PS_CHECK_UPDATES`, `PS_COLLECT_LOGS`, `PS_HARDWARE_SCRIPT`, `PS_COLLECT_FAILED_LOGINS`. These are the **only** PowerShell payloads sent by the v2 collector.

**Why centralise**: prevents drift between v1 and v2 copies of the same script (a class of bug we hit during the v1 retirement). All check functions import these constants by name.

## DS-118 — HTTP API surface

**Implements**: FS-007, FS-008, FS-013, FS-019, FS-020, FS-030–FS-040, FS-050–FS-062, FS-070, FS-074, FS-075, FS-083, FS-094, FS-121, FS-124.

## DS-120 — Database access patterns

**Implements**: FS-079, FS-080, FS-081, FS-091, FS-092.

**Structure**: `database.py:Database` is a thin DAO with:
- `_write_lock: threading.Lock` — serialises every method that writes (`insert_metric`, `insert_event`, `log_audit`, `cleanup_old_data`, etc.). Reads are lock-free thanks to WAL mode.
- `_get_conn()` — opens a new connection per operation; `PRAGMA journal_mode=WAL` + `PRAGMA busy_timeout=5000`.

**Why single write lock**: SQLite's WAL allows concurrent readers and one writer, but a second writer blocks. The lock makes that contention explicit (and fast — no thread can hold it for long).

**Why per-operation connection**: avoids long-lived thread-affine connections that complicate the write-lock contract. Connection-open cost is negligible against WinRM call latency.

## DS-121 — Pulse / heartbeat data flow

**Implements**: FS-008.

**Producer**: `collector_v2/aggregator.py:_process_result`'s `finally` block calls `state.record_pulse(ts, server, check_type, ok, duration_ms)` for every `Result` regardless of check type.

**Buffer**: `state._pulse_buffer: deque(maxlen=1000)` — wrap-around, so the most recent 1 000 events are always available regardless of fleet size or check cadence.

**Reader**: `routes/api/health.py:/api/collector/pulse` polls `state.get_recent_pulses(since_ts, window_s=12.0)` + `state.get_fleet_status(now)` + subsystem heartbeats. Returns the JSON shape consumed by `static/js/pulse-monitor.js`.

**Browser**: `static/js/pulse-monitor.js:PulseMonitor` polls every 1.5 s with `?since=<watermark>` so payload stays tiny on steady-state. Canvas `requestAnimationFrame` loop scrolls at ~10 FPS. Pauses entirely after 5 s with no events.

## DS-122 — Recovery / backup procedure

**Implements**: FS-094, FS-095.

**Backup**:
- `tools/backup.py` produces a timestamped zip containing `prism.db`, `config.json`, `data/install_state.json`, key file (`data/.key` or env-pointed location), and any custom backup files.
- Run on demand from the CLI or scheduled via OS task scheduler.

**Restore**:
- `tools/restore.py` accepts a backup zip + a target directory; unpacks atomically (temp dir → swap).
- Restoration before Prism starts. Restoration while Prism is running is unsupported (would corrupt WAL).

**Re-key**:
- `tools/rekey.py` writes a new key file, re-encrypts every encrypted password in `config.json`, replaces the old key file atomically.

**Procedure**: `docs/BACKUP_AND_RESTORE.md` and `docs/KEY_ROTATION.md`.
